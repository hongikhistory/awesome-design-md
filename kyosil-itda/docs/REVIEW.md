# 교실잇다 1차 MVP 비판적 검토

세 관점(대회 심사위원, 개발 전문가, 학교·교육실습 현장 전문가)에서 1차 MVP(커밋 `cd31b38`)를 검토했다. 근거가 있는 지적만 담았고, 각 항목에 이번 2차 개선에서 한 조치를 적었다.

- 심각도: **상**은 수상이나 실사용을 막는 문제, **중**은 신뢰를 떨어뜨리는 문제, **하**는 다듬을 문제.
- 측정 근거: axe-core 4.10.3 접근성 검사(7개 화면), Playwright 동시 쓰기 실험, 화면 캡처 검토.

## 1. 심사위원 관점

| # | 지적 | 근거 | 심각도 | 조치 |
|---|---|---|---|---|
| J1 | 화면이 “AI가 만든 SaaS”처럼 보인다. 이모지 아이콘(☀ ✉ ⇄ 🔒), 모든 상태에 붙은 알약 배지, 모든 블록에 그림자 카드가 반복된다. 학교 현장의 시각 언어가 없다. | 1차 화면 캡처 | 상 | 공공 서비스 표준인 **KRDS(대한민국 정부 디자인 시스템)** 공식 토큰으로 전환했다. 이모지는 Lucide 선 아이콘으로 바꿨고, 결재는 공문 **결재란** 형식으로, 시간표와 보고서는 학교 서식 표 형식으로 바꿨다. |
| J2 | 교육적 근거가 약하다. 교생실습 흐름이 “메모→평가→피드백”으로 임의 구성돼 있고 교육학 이론과 연결되지 않는다. | `Practicum.tsx` 탭 구성 | 상 | 임상장학(Cogan·Goldhammer) 3단계 **계획 협의 → 수업 관찰 → 피드백 협의**로 재구성했다. 계획 협의에서 교생이 “관찰 받고 싶은 초점”을 정하고, 관찰 화면이 그 초점을 강조한다. |
| J3 | 첫 화면에서 무엇을 봐야 할지 모른다. 심사는 5분 안에 끝나는데 시연 동선이 사용자 전환에 의존한다. | 1차 `Today` 화면 | 상 | 단계별 **시연 안내**를 넣었다. 버튼 하나로 사람과 화면을 바꿔 가며 7단계를 따라간다. |
| J4 | 문제 제기가 특정 설치형 제품 분석 수치에만 기대고, 사용자 조사가 없다. | `About.tsx` | 중 | 수치는 “설치형 구조 일반의 사례”로 비중을 낮췄다. 아직 하지 않은 현장 검증은 **검증 계획**(설문 문항, 측정 지표)으로 명시했다. 하지 않은 조사를 한 것처럼 쓰지 않는다. |
| J5 | “AI”라는 말이 과장으로 읽힐 수 있다. 추천은 가중 점수이다. | `cover.ts` | 하 | “설명 가능한 규칙 기반 추천”으로 표현을 통일했다. |

## 2. 개발 전문가 관점

| # | 지적 | 근거 | 심각도 | 조치 |
|---|---|---|---|---|
| D1 | 중계 저장소가 전체 상태를 읽고 고쳐 다시 쓰는 구조라 여러 탭이 동시에 쓰면 데이터가 사라진다. | 두 탭이 같은 패턴으로 80건을 쓰는 실험에서 38건이 사라짐(지연을 넣어 재현). | 상 | 봉투·방·공개 키를 **항목마다 별도 키**에 저장해 공유 데이터를 읽고 고쳐 쓰는 과정을 없앴다. 동시 30건 쓰기 통합 테스트에서 유실 0건이다. |
| D2 | 암호화-서명-중계-복호화 전체 경로를 검증하는 테스트가 없다. 단위 테스트가 부품만 본다. | `core.test.ts` | 상 | 엔진 통합 테스트를 추가했다. 비구성원 차단, 키 교체 후 퇴장자 차단, 신규 참여자의 과거 열람 불가, 서명 위조, 미래 시각 위조를 다룬다. |

| D4 | 승인 순서가 클라이언트가 붙인 시각에 의존한다. 악의적 구성원이 과거나 미래 시각을 붙일 수 있다. | `reduceRequests` 정렬 | 중 | 현재 시각보다 5분 넘게 미래인 이벤트는 거부한다. 실제 서버에서는 중계 서버가 시각을 찍어야 한다는 점을 한계로 명시했다. |

| D6 | 화면 상태가 바뀔 때마다 모든 방을 다시 복호화한다. 규모가 커지면 느려진다. | `readAll` | 하 | 평문 캐시로 대부분 피하고 있다. 증분 처리는 로드맵에 남긴다. |

## 3. 현장 전문가 관점 (교무부 시간표 담당, 교육실습 지도교사)

| # | 지적 | 근거 | 심각도 | 조치 |
|---|---|---|---|---|
| F1 | 학교는 보결보다 **수업 교체**를 먼저 찾는다. 교체는 수업 결손과 추가 수당이 없기 때문이다. 보결만 추천하면 실제 업무 순서와 맞지 않는다. | 1차는 공강 교사 보결만 추천 | 상 | **교체 우선 제안**을 추가했다. 같은 학급을 맡은 교사 중 맞바꿀 수 있는 시간이 있으면 보결 후보보다 먼저 보여 준다. |
| F2 | 형평성 점수가 있어도 교사들은 “누가 몇 번 했는지”를 직접 보고 싶어 한다. 점수만으로는 납득이 어렵다. | 보결 횟수가 화면에 없음 | 중 | 학교 전체 **보결 현황표**(최근 4주 횟수, 이번 주 반영 건)를 추천 화면에 붙였다. |
| F3 | 교생도 지도교사와 다른 교사의 수업을 참관하고 참관록을 쓴다. 1차는 지도교사만 메모할 수 있다. | `Observe` 권한 | 중 | 교생도 참관 기록을 남길 수 있게 바꿨다. 메모마다 작성자를 표시한다. |
| F4 | 실습 공간을 만드는 흐름이 없다. 시드 데이터로만 존재한다. 실제로는 실습 첫날 지도교사가 교생을 맞이한다. | 생성 화면 없음 | 중 | 지도교사가 교생과 보존 기간을 골라 **실습 공간을 여는 화면**을 추가했다. |
| F5 | 결재는 학교에서 “결재란” 형식으로 익숙하다. 진행 막대보다 담당, 직위, 서명, 날짜 칸이 더 빨리 읽힌다. | 1차 3칸 진행 막대 | 하 | 결재란 형식으로 바꿨다(J1과 함께). |
| F6 | 인수인계서에 학생 이름을 쓰지 말라는 안내는 좋지만, 보결 교사에게 필요한 “좌석표·출석 확인 방법”이 빠져 있다. | 카드 필드 | 하 | 남은 과제로 기록했다. 개인정보 문제와 충돌하므로 학교 협의가 필요하다. |

## 4. 이번에 하지 않은 것

- 실제 중계 서버, 기기별 키 생성, Web Push 알림: 서버 인프라가 필요하다.
- NEIS 시간표 연동: 범위 밖이다.
- 사용자 조사: 실제로 하지 않았으므로 결과를 만들지 않았다. `README`의 검증 계획으로 대신한다.

## 5. 검토 중 추가로 찾은 문제

- **대화방 기본 선택이 실행마다 달라짐:** 시드 방 두 개가 같은 밀리초에 만들어지면 정렬 순서가 바뀌어, 같은 사람이라도 다른 방이 먼저 열렸다. E2E 실행 3회 중 1회꼴로 실패해 발견했다. 최근 활동순으로 정렬하고, 한 번 연 방은 새 메시지가 와도 바뀌지 않게 고쳤다.
- **다른 지도교사의 교생을 다시 배정할 수 있음:** 배정 여부를 내가 열 수 있는 방으로만 판단했기 때문이다. 배정은 서버가 이미 아는 방 구성원 정보이므로 그것으로 판단하게 고쳤다.
- **결재란 칸 밀림:** 세로 “결재” 칸이 머리글에만 걸쳐 도장이 한 칸씩 밀렸다. 하나의 표 본문으로 다시 구성했다.
